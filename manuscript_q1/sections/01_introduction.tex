\section{Introduction}
Suppose a team can review five npm maintainer accounts. Its choice determines which downstream applications it can associate with those accounts. A dependency graph grouped by package name can connect edges that refer to different versions of the same package. Requiring the versions to match along a path can change the account ranking and, with it, the list of applications in scope. Prior research measures upstream npm leverage and coordinated dependency changes~\cite{samaana2025,he2025}. We evaluate the coverage consequences of that choice using pinned application lockfiles and exact-version registry observations.

The ranking also depends on what the team wants to cover. Adding an account may reach few new repositories if most are already within scope. The same account can still account for many distinct account--repository pairs and can complete the set of observed sources for some repositories. We measure these tradeoffs in the graph and evaluate the representation choice using a separate set of application-owned records.

The original graph comes from an expansion seeded by high-impact npm packages. It contains 25,228 identifiers, including bundled contexts, and 12,217 observed usernames. We evaluate reach over 7,171 normalized repository keys associated with observed workflow directories. We compare ranking and greedy-coverage baselines, weighted combinations of objectives, and a heuristic that prioritizes all-source exclusion.

We vary the heuristic's components and compare its results with exact optima on restricted candidate sets. Fresh dependency, maintainer and workflow observations from 100 sampled roots let us check which findings repeat in a bounded cohort. We also use a stratified probability sample of 120 endpoints to characterize commit-pinned evidence for repository mappings and workflow files. The endpoint indicators are automated and lack manual validation.

We ask five questions.
\begin{itemize}
\item \textbf{RQ1:} How large are the observed coverage, additive-exposure and all-source-exclusion tradeoffs at equal budgets?
\item \textbf{RQ2:} How do representation choices affect evaluation, and what evidence supports the workflow-associated endpoint observations?
\item \textbf{RQ3:} How sensitive is the exclusion-oriented heuristic to its components, candidate cap and ties, and where does it miss candidate-restricted optima?
\item \textbf{RQ4:} Which tradeoffs persist in a separately collected cohort and among endpoints and accounts observed in both datasets?
\item \textbf{RQ5:} At the same account budget, which held-out applications change documented coverage with the graph representation, and how much uncertainty remains?
\end{itemize}

Our main contribution is a paired comparison of documented downstream coverage under a fixed account budget. We freeze the five-account name and version portfolios before collecting evidence from Awesome-Selfhosted and YunoHost. Five YunoHost applications have confirmed switches, and we bound turnover over the full frames, including unresolved cases. In the graph experiments, we quantify the loss in distinct repository coverage when the ranking prioritizes modeled exposure. We also measure how often the exclusion heuristic falls short of an exact solution on restricted candidate sets.
