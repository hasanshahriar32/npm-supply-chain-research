TITLE
Maintainer Prioritization in npm Supply Chains: Objectives, Representation Sensitivity, and Metadata Limits

ABSTRACT
\textbf{Context.} Teams can use npm dependency graphs to decide which maintainer accounts to review. Grouping dependencies by package name can join edges that refer to different versions, changing which accounts a ranking selects.

\textbf{Objective.} We test whether preserving exact-version paths changes which downstream applications fall within a fixed account review budget.

\textbf{Method.} We selected five accounts from each graph representation before examining two held-out catalogs of self-hosted applications. For each application, we traced declared production dependencies in committed lockfiles and linked locked package versions to observed npm maintainer records. We bounded turnover, the share of applications with a documented path to exactly one account selection, by keeping unresolved comparisons in the denominator.

\textbf{Results.} In YunoHost, 164 of 215 comparisons were resolved. Three applications had documented coverage only under the name-based selection and two only under the version-based selection. Turnover was bounded at 2.3–26.0%. In Awesome-Selfhosted, 88 of 155 comparisons were resolved. We found no confirmed coverage changes, with turnover bounded at 0–43.2%. In both catalogs, the evidence allowed either selection to cover more applications overall.

\textbf{Conclusion.} Changing the graph representation can bring some applications into review scope and drop others at the same budget. Comparing the application lists reveals changes that a total coverage count can hide.
